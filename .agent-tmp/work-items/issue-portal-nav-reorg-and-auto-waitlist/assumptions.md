# Assumptions & Design Decisions

## 1. 候補名額自動遞補轉正
- **背景**：原機制在時段釋出空位時，會保留 30 分鐘讓第 1 順位候補家長登入網站手動點擊「確認轉正」。
- **決策**：依 PM 需求拿掉 30 分鐘確認等待機制。一旦時段有名額釋出（例如前面有人取消預約），系統直接為第 1 順位候補學生轉為 `Confirmed` 正式預約、扣抵堂數（付費/贈送）、將候補狀態設為 `ConfirmedToBooking`、自動推進後續候補順位（第 2 順位變第 1 順位），並立即發送 LINE 推播通知提醒家長準時出席。

## 2. 備註說明來源查核
- **查核結果**：學籍歷程中的「備註說明」在兩處業務情境下輸入：
  1. **退班批次結算**：管理員在退班試算列表中點擊「退班結算」時輸入之原因備註。
  2. **學期續報**：學期結束或學籍異動時，管理員/老師執行學籍續報（`RenewStudentAsync`）時所填寫之備註。

## 3. 功能遷移與架構整併
- **帳號與學生綁定** & **學期與每週進度**：從原本「管理員營運與報表」頁面搬移至「學生 / 家長 / 老師管理」，使成員、帳號、權限與學期開課進度統整於同一個管理入口。
- **按鈕與彈跳視窗**：原帳號頁面頂部佔據大面積空間的「建立登入帳號」與「家長 ↔ 學生綁定」表單改為 2 顆清晰按鈕，點擊彈跳 Modal；預設直觀呈現全系統登入帳號清單與密碼重設列表。
- **學生與到班目的**：確認為重複/多餘功能，全數移除。

## 4. 三方對帳 22 筆異常檢視與修復
- **成因**：系統對帳比對「學生主檔付費堂數」、「不可篡改流水帳累積差額」與「儲值批次 RemainingPaidCredits 總和」。因前期種子資料或遷移資料尚未為部分在籍學生補建儲值批次，導致比對出 22 筆帳務不一致。
- **解決**：在對帳紅條加上「立即檢視異常明細清單」按鈕，打開 `#modalReconciliationDetails` 顯示 22 筆異常學生的主檔、流水帳與批次差額明細，並提供「一鍵自動同步校準」按鈕，呼叫 `DbInitializer.EnsureCreditBatchesAndLedgerConsistentAsync` 自動同步補齊差額。

## 5. 本輪 SQL 執行需求評估
- **結論**：本次調整純粹涉及**業務流程自動化（候補轉正）、頁面 UI 結構重組、彈跳視窗化、中文翻譯與頁籤視覺簡化**，**無任何資料庫 Schema 異動（無新增/刪除資料表或欄位）**，因此**不需要執行任何 SQL 指令**。
